# 公交轨迹迁仓 API

公交定位点原先**按采样日入仓**（旧仓），跨夜班次的两段轨迹被拆在两天。本服务把轨迹
**按发车日（UTC）归仓**（新仓），支撑运营日报"跨夜整趟轨迹归到发车日"的口径。

- FastAPI + SQLite，Docker Compose 一键启动，交互文档在 **`/docs`**
- 数据员**逐日回填**（导入班次、发车时刻、带编号定位点），核对后**按日切换供数来源**
- 未切换的日期仍从旧仓取数；回填后轨迹有变时切换被退回并提示重做
- 切换前后均可补传点位、更正发车时刻；班次改期时整趟轨迹随之换日

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000/docs
```

本地开发（Python 3.11+）：

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --reload
```

端到端演示（需先启动服务，针对**全新数据库**执行；重复执行会叠加旧仓点位）：

```bash
scripts/demo.sh            # 或 BASE=http://host:port scripts/demo.sh
```

## API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/legacy/points` | 灌入旧仓点位（按采样日入仓）。模拟既有旧仓，仅演示/初始化用 |
| POST | `/trips/import` | 导入班次、发车时刻、带编号定位点。回填/补传/更正/改期共用，切换前后均可调用 |
| GET | `/dates/{date}/state` | 查看某日回填状态指纹（班次/时刻/当前提交内容的哈希） |
| POST | `/dates/{date}/switch` | 携带回填时确认的指纹，切换该日供数来源到新仓 |
| GET | `/trips?date_from&date_to` | 按日期范围查询轨迹（单次跨度 ≤31 天） |

所有时间均按 **UTC**：请求可带任意时区偏移（如 `+08:00`），服务端统一归一化为 UTC
后再取日期；无时区的时间串会被 422 拒绝。

## 实现

### 数据模型（SQLite，`app/db.py`）

- `legacy_points`：旧仓，点位按 `sample_date`（采样时刻的 UTC 日期）归集
- `trips`：班次，`departure_at` → `departure_date`（UTC 发车日），
  `active_in_new` 标记是否已切到新仓供数
- `batches` + `points`：每次点位导入生成一个**全量快照批次**（版本号按班次递增），
  `trips.current_batch_id` 原子指向最新批次
- `date_switches`：已切换的供数日期（单向，不回退）

### 关键语义（`app/service.py`）

1. **逐日回填**：`POST /trips/import` 接收班次+发车时刻+带编号点位；响应返回每个
   受影响日期的状态指纹，供数据员核对。
2. **切换守卫**：切换请求必须携带回填核对时的 `state_token`。指纹覆盖该日全部班次的
   发车时刻与当前批次内容哈希——回填之后任何变更（补传点位、更正时刻、改期进出该日）
   都会改变指纹。不一致时返回 **409** 并提示"重新核对（重做回填确认）后再切换"，
   响应附带当前指纹。切换幂等：重复切换返回 `already_switched`。
3. **供数规则**（`GET /trips`）：
   - 已切换日期：从新仓取 `departure_date = 当日` 的班次，**整趟轨迹（含跨零点点位）
     归到发车日**；
   - 未切换日期：从旧仓按采样日切片供数；
   - 班次一旦激活（所在发车日被切换，或导入/改期进入已切换日），**激活状态粘滞**：
     改期到未切换的日期，整趟轨迹仍从新仓供数——改期换日与两天的供数来源无关；
   - 已激活班次的旧仓点位在**所有日期被抑制**，因此范围查询中**每趟车只出现一次**。
4. **同一提交状态**：点位按全量快照成批提交，查询只读当前批次；一次请求一个事务，
   不会读到两个批次混杂的点位。响应中的 `batch_version` 可供核对。
5. **改期**：更正发车时刻导致 `departure_date` 变化即整趟换日（点位挂在班次上，
   天然整体迁移），导入响应以 `rescheduled: true` 标识，并返回新旧两个日期的指纹。

## 自测

### 单元/接口测试（12 个用例，全部通过）

```bash
.venv/bin/python -m pytest tests/ -q
```

覆盖：

- **跨夜归仓**：23:40 发车、轨迹跨零点，切换后整趟归到发车日，次日不再出现该班次；
- **未切换走旧仓**：切换前查询结果与旧仓一致（跨夜班次按采样日拆两天）；
- **过期回填守卫**：回填后补传点位/更正时刻 → 指纹变化 → 旧指纹切换返回 409 并提示
  重做 → 新指纹切换成功；
- **切换前后均可更正**：切换后补传点位、更正发车时刻即时生效，日期保持已切换；
- **改期（双向）**：已切换日 → 未切换日、未切换日 → 已切换日，整趟轨迹随之换日，
  每趟车只出现一次，旧仓对应点位被抑制；
- **同一提交状态**：二次提交后查询只含最新批次点位，无历史版本残留；
- **UTC 归一化**：`+08:00` 与 `Z` 的同一时刻归同一发车日，不算改期；
- **参数校验**：编号重复、缺发车时刻、无时区时间、区间倒置/超长均 422；
- **切换幂等**：重复切换返回 `already_switched`。

### 端到端演示

`scripts/demo.sh` 对运行中的服务完整走一遍：灌旧仓 → 回填 → 回填后变更 → 旧指纹
切换被 409 退回 → 重新核对切换 → 跨夜归仓查询 → 改期到未切换日 → 切换后更正。
已在本地以 `uvicorn app.main:app` 验证通过（输出符合上述每一步预期）。

## 遗留事项

- **未做容器内验证**：交付环境无 Docker，`Dockerfile`/`docker-compose.yml` 经静态核对，
  未实际 `docker compose up`；应用本身已在本地以相同入口（`uvicorn app.main:app`）验证。
- **无鉴权**：未接账号/权限，导入与切换接口对内网开放；上线前需加认证与操作审计
  （谁回填、谁切换）。
- **切换单向**：不支持把日期切回旧仓；如需回滚要另加管理接口并定义旧仓回补口径。
- **未切换日的跨夜班次仍按采样日拆分**：这是"未切换仍从旧仓取数"的既定口径；只有
  切换（或班次激活）后才有"整趟归发车日"的视图。
- **点位提交为全量快照**：补传点位需提交整趟最新全量点位；若旧仓侧有点位级订正流，
  需要增量合并接口（当前版本未做）。
- **规模限制**：单机 SQLite + 单进程；范围查询限 31 天；无分页。数据量上来后需换
  外部数据库并加分页/异步导出。
- 测试环境 `httpx==0.28.1` 与当前 starlette 的 TestClient 有一条弃用告警，仅影响
  测试输出，不影响运行。
